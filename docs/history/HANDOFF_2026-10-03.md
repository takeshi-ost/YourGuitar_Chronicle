## 今回確定したレイアウト

### Top Page / User Profile

- Product Detailの高さはブラウザ表示領域からヘッダーと上下28pxを引く。
- 各ギターリストは未フィルタの件数から高さを計算し、Detailの高さを上限にする。少数は短く、多数は内部スクロール。
- フィルタで件数が減っても外枠の高さを変えない。データ更新・ブラウザサイズ変更・ツールバーサイズ変更時に再計算。
- `sizeGuitarList` / `measureGuitarList` が行の高さと周辺要素を測り、`--list-content-height` を設定する。現在の行は一行表示。将来折返しに変える場合は測定方法も見直す。
- New discoveryとProduct List間は16px。
- User Chronicleは内容の自然な高さと同じDetail上限を使う。現在フィルタ機能はない。
- 上記のDetail連動は幅901px以上。狭い画面では独立した高さを維持。

### Browser Console

- Product DetailとUser Detailの内部だけスクロール。通常のページ配置を維持。
- Backup操作欄はGuitar DB左列の先頭へ、Open Top Page as Guest等の操作欄はUser DB左列の先頭へ移動。
- 操作欄の横幅はリスト列に合わせる。右のDetail上端を操作欄上端へ引き上げる。
- 右のDetailは移動前の下端位置を保つため、デスクトップ時のみ操作欄の高さ＋下余白を追加する（`--detail-raised-space`、ResizeObserverで計測）。このためDetail全高は表示領域より大きくなることがある。今回の依頼どおり。

## 係争機能の現在仕様（PR #9まで）

詳細は `docs/features/OWNERSHIP_DISPUTES.md`。実装は `disputes.py` / `dispute_routes.py` / `static/disputes.js`。

- 正式Acquireのうち現在Ownerを置き換えるものだけ対象。Formerly Owned登録には係争導線なし。
- OwnerのDecline理由必須。申請者が納得なら終了、異議申立てで説明・要旨・添付を提出して係争開始。無回答の運営確認依頼は既定14日後。
- Current Ownerを維持し、所有関係のClaimの追加・編集・削除・承認を停止。所有に影響しない投稿は継続。
- 各ラウンドでAcquireごとに双方1回ずつ提出。双方提出済みをUnder reviewとする。
- 管理者の裁定は未提出・片側提出・審査中のどの段階でも可能。理由必須。
- 追加証拠要求は双方提出後に次ラウンドを開始。原本・説明は提出者と管理者のみ。他方は管理者が公開した要旨のみ閲覧。
- 管理者は原Owner支持／申請者支持を決定。Claim作者は書き換えず、判定済みClaimを通常Verificationで変更できないようロック。
- 終了案件の変更は理由付き再審議。既に別Ownerへ移った案件は再開不可。
- UIは上部Acquire情報、Round別時系列、末尾Review result。提出可能な場合のみフォームを表示し、提出直後にサマリー追加・フォーム非表示。
- 開始・追加要求の重複履歴行は省略。証拠待ちのReview resultは非表示。
- 提出後AcquireモーダルのフッターはOKのみ、申請を変更せず閉じる。
- 公開環境の認証は未実装。ローカル試作の権限境界である点は公開移行前に対処する。
