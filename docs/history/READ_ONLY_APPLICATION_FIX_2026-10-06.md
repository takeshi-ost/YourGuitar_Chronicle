# Cloud申請のRead-only UI回帰修正 — 2026-10-06

## 対象と原因

ベースは公開main `6080296ef353437af98a0de05e91f3fe6b0a4f0a`。
作業ブランチは `fix/read-only-application-ui`。従来の作業チェックアウトは変更せず、別のclean cloneで修正した。

実サービスの受入確認で、Read-only中も本人のPending ListingのCancelが押せ、サーバーの403拒否後に本人の申請一覧が消える不具合が見つかった。写真の閲覧とサーバーの変更拒否は機能していた。

原因は次の2点。

- クライアントが申請変更の可否を取得せず、Create・Submit・Cancel・Retryをbusy状態だけで制御していた。
- 申請APIがサービスモード制限と本人の認可失効を同じ403へ変換し、クライアントも一律に一覧を消していた。

## 変更

- GET `/api/auth/applications` に `can_write` を追加。同じ本人確認・サービスモードの共有ロック・申請読取トランザクションの状態から判定する。Read-onlyではAdmin本人の申請も変更不可。Admin-onlyでは既存のcanonical Admin用のアクセス規則を維持する。
- サービスモードの拒否だけを403 `detail.code=service_restricted` で区別する。一般の401/403と詳細を混同せず、非公開情報をエラーへ含めない。
- 変更可否がtrueになるまで全申請変更を無効化する。無効なボタンのhandlerが直接呼ばれても変更リクエストを送らない。写真入力と写真閲覧ボタンを分け、Read-onlyでも本人の写真と詳細を閲覧できる。
- 変更要求後にモードが変わっていた場合は一覧を再取得。同一アカウント・同一セッションで読取が再確認できた場合だけ一覧を維持する。認証失効、読取拒否、復旧読取失敗では詳細・写真URL・一覧を消去する。一般の非認証エラーでは申請一覧とエラー表示を保持する。
- ダイアログ内にRefreshを追加し、ウィンドウへの再フォーカスでも一覧と変更可否を更新する。開いた入力内容をモード確認だけで消さない。Read-onlyへの移行でRetryの確認段階を解除する。
- 取消成功後にダイアログが閉じていても一覧を更新し、閉じたダイアログを開き直さない。古い成功・失敗・写真・一覧の応答が別アカウントやSignOut後のセッションへ反映されないよう保護する。

常時push通知・ポーリングは追加していない。別の管理者が現在アクティブなタブの閲覧中にモードを変更した直後は、次のRefresh／再フォーカスまでボタンが古い状態になる可能性がある。その間もサーバーの既存制限は有効で、拒否時に本人の読取可否を再確認する。

1. 差分をレビューし、commit・push・draft PR作成を個別承認してから実施する。このチェックポイントでは未コミット・未push・PR未作成。
2. 許可されたCIで既存の必須チェック `Tests (Python, JavaScript, Chromium)` を最新commitに対して実行する。追加した実Chromium／PostgreSQL回帰を含む全チェックの成功を確認する。
