# 管理者権限とメンテナンス制御の最終仕様・ローカル維持方針

2026-10-04の方針整理。クラウドの管理API・モード判定・初回Admin付与Jobは実装済み。[クラウドConsole](CLOUD_BROWSER_CONSOLE.md)の状態確認・モード操作を接続した。BrowserConsoleのデータ管理、コンテンツAPI、復元・リセット、ジョブ排他への接続は未実装。実装範囲は[クラウド管理API](CLOUD_OPERATIONS_ACCESS.md)を参照。メンテナンス中にReset DBを実行できず、Normalへ戻す必要があった不整合を解消するための仕様である。

## 基本方針

メンテナンスは一般利用を制限し、管理者が修復・確認・復旧するための状態とする。管理者資格、サービスモード、個々の操作の実行条件を別々に判定する。Adminでも所有権の業務規則や復元・リセットの停止条件を無条件に迂回できるわけではない。

## GCP移行後の最終仕様

AdminはUser Typeとは独立した権限。Identity Platformの検証済み主体をAccountsの固定ユーザーIDへ解決し、サーバー側の有効な管理者資格を確認する。画面のユーザー選択、リクエストのuser_id、メール・表示名だけでは付与しない。権限解除・BAN・アカウント無効化は古い認証情報だけで許可し続けない。

| モード | Guest・一般利用者 | 認証済みAdmin |
| --- | --- | --- |
| Normal | 通常の閲覧・許可された更新 | 通常利用と管理操作 |
| Read-only | 公開・本人権限の範囲で閲覧可能。更新停止 | 管理画面の閲覧・修復・設定変更・許可された管理更新 |
| Offline | メンテナンス案内・認証／復旧に必要な限定入口のみ | 管理画面の閲覧・修復・設定変更・許可された管理更新 |
| Admin Only | メンテナンス案内。一般の閲覧・更新停止 | 管理操作に加え、通常画面でも既存の閲覧・業務権限の範囲で試験可能 |

Offlineは一般サービス停止、Admin Onlyは管理者による通常画面での試験を目的とする。Read-only / Offlineでも管理者として通常のユーザー更新を自動的に通すのではなく、明示的な管理経路を使用する。Admin Onlyでも自己Claim判定禁止等の通常業務規則は維持し、強制判定は監査される管理用別経路とする。

管理画面の表示と、そのためのデータ読取・画像配信にも同じ資格確認を適用する。非公開根拠を含む取得には個別の閲覧権限が必要。URLの接頭辞や管理画面からのアクセスであることだけを許可根拠にしない。

### 操作条件

- 状態確認、モード変更、バックアップ一覧・保存・ダウンロードは全モードで管理者に許可する。保存時のジョブ競合条件は維持する。
- 復元とDBリセットはRead-only / Offline / Admin Onlyを必須とする。書込・Crawl・審議反映・定期ジョブを停止し、実行中処理が終了したことを確認してから排他的に実行する。Normalでは拒否する。
- Resetは対象・環境の表示と確認入力を要求し、対象別の事前バックアップを保存する。公開前の全試験データリセットと、Chronicle単独リセットを分ける。公開後の全消去は通常運用の対象にしない。
- モード変更だけで、既に開始したジョブの停止・排他が完了したとみなさない。初期化前のGPT回答やジョブが新しい世代へ書き込まない制御を設ける。
- 手動Crawl・再処理・データ修復は管理者が明示的に開始する操作として扱い、排他中は拒否する。自動Crawl・自動審議反映は非Normalでは停止する。回答の受信・保持とDBへの反映を分ける。
- 復旧は自動的にNormalへ戻さず、管理者が整合確認後に明示的に切り替える。

権限付与／解除、モード変更、破壊的操作、強制判定は操作者・対象・結果・時刻を監査する。モード、権限、排他・ジョブ状態は複数インスタンスで共有する。管理者の認証入口とモード解除経路はメンテナンス中も利用可能にする。

## GCP接続までのローカル維持方針

2026-10-04、ユーザー合意によりローカルは現状でよしとする。Console資格を使ってメンテナンス制限を迂回する暫定変更は実装しない。既存のloopback限定Console資格と現在の操作条件を維持する。

- Reset DBはNormalで実行する。Auto Crawl・審議反映をOFFにし、実行中Crawlの終了と事前バックアップを確認する。
- バックアップ復元は現在のRead-only / Offline必須条件を維持する。
- メンテナンス中の一般更新停止と、既存のOperations等の例外も維持する。

管理者によるメンテナンス中の編集・Reset・修復の制御変更はGCP移行時に、認証済みAdminと合わせて実装する。GCP移行後にBrowser Consoleからの編集を再テストし、以下の受入確認を実施する。これはローカル整備の必須残作業には含めず、公開前のGCP検証項目として扱う。実装後に[操作ガイド](../operations/README.md)と既存テストの期待値を更新する。

## 受入確認

- 各モードでGuest・一般利用者・資格なし／不正資格・有効な管理者の閲覧と更新を直接APIでも確認する。
- メンテナンス中のReset・復元・設定変更・管理画面の必要読取が許可され、一般利用の書込が拒否される。
- 実行中ジョブ・排他競合・古い世代のGPT回答でResetや復元の整合が壊れない。操作失敗時も勝手にNormalへ戻らない。
- Chronicleリセット／復元でAccountsを巻き戻さず、ID対応・画像・投影が整合する。
- 所有権の変更を含む管理操作では[設計上の不変条件と遷移例](../architecture/CLAIM_CENTERED_ARCHITECTURE.md)を検証し、通常Ownerの操作と管理者強制判定を別経路で確認する。
- GCPでは権限解除・複数インスタンス・非公開画像・Admin Onlyの通常画面試験も確認する。

初期化範囲と公開前の再リセットは[GCP移行境界](GCP_BOUNDARIES.md#初回移行と公開前のdbリセット方針2026-10-04)、現行の運用機能は[サービス運用仕様](../features/SERVICE_OPERATIONS.md)を参照。
