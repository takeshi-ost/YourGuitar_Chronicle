# Cloud Runの本人アカウント画像

2026-10-04。Cloud Storage接続基盤の次段階として、認証用Accountページに本人の画像の保存・再表示・削除を追加した。ギター・Claim・申請の根拠画像の移行は別段階。

## 操作と権限

メール確認済みの登録ユーザーがAccountページでJPEG・PNG・WebPを選び、Save imageで保存する。再読み込みやSign In後も再取得する。Remove imageは現在の表示用参照を解除する。SignOutで画像表示と一時URLを破棄する。

通常操作は `GET / PUT / DELETE /api/auth/avatar`。本人はGoogleの検証済みトークンからAccounts正本のUUIDへ解決し、クエリによる他ユーザー指定を拒否する。未確認メール・無効アカウント・不正トークンを拒否する。通常の閲覧・更新はサービスモードに従う。

Accounts正本でAdminの本人だけは、明示的な `/api/admin/accounts/me/avatar` を使う。管理者操作としてメンテナンス中も使用できる。他のユーザーの画像を変更するAPIではない。Admin資格とサービスモードはDB操作中もロックして再確認する。

画像障害や通常ユーザーへのメンテナンス制限で、認証・SignOutの機能を停止させない。現段階では他ユーザーへの公開配信は設けない。

## 画像とDBの契約

入力は最大8MiB、800万画素、静止画のみ。実際の画像形式とMIMEの一致を確認する。向きを補正し、最大512×512へ縮小、透過部分を白にしたJPEGに正規化する。EXIFや元のファイル名は保存しない。画像処理の並列数を1に制限する。

実体は非公開accountsバケットへ一意のキーで保存する。Accountsの既存 `avatar_storage_path` に `gcs-avatar-v1:` に続くscope・name・generation・size・content_typeの参照を保存する。既存カラムを使うためDDL更新は不要。ローカルパス・URLへのフォールバックはしない。Accounts投影ではこの参照をコンテンツDBにコピーするが、コンテンツ側の画像取得接続は後続作業。

画像の取得はBearer付きの同一オリジンAPIを経由し、固定generationで取得する。レスポンスはprivate/no-storeとnosniff、ブラウザはBlobの一時URLで表示する。トークンをURLへ含めず、バケット公開・署名URLの配布もしない。

## 更新失敗とバックアップ

Accountsの参照更新・監査記録・既存の投影outbox更新は同一トランザクション。AccountsをコミットするまでOperationsのモードロックを保持する。監査失敗などコミット前の失敗では新しく作った世代だけを補償削除する。コミット結果が不明な障害では、保存済み参照を壊さないよう候補画像を保持する。

更新前の画像やRemove imageで解除した画像は、以前のAccountsバックアップから復元できるよう実体を保持する。Remove imageは物理的な完全削除ではない。バックアップの保持期間と整合する孤立画像回収・完全削除の運用設計は未実装。対象別バックアップ／復元のCloud Storage接続も後続作業であり、画像の独立した完全復元を保証する段階ではない。

## 検証

画像正規化、不正参照拒否、本人限定の認証、入力制限、監査失敗の補償、コミット結果不明時の保持を単体検証する。隔離した実PostgreSQLでは全サービスモードとAdmin／一般ユーザーの組み合わせ、参照と監査のロールバック、資格とモードの競合排除を確認する。ブラウザでは保存、再読み込み、削除、SignOutの表示破棄を確認する。外部認証・保存はこのブラウザ検証だけで代替し、実ステージングの利用者操作とは区別する。
